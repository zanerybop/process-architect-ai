# Тестовый корпус

15 синтетических описаний. Входы — inputs/P01.txt ... P15.txt.
cases.json содержит ожидаемый результат и семантические ограничения.
Нет готовых .bpmn и нет утверждения, что эти проверки уже пройдены.

P01–P06, P10–P11, P13 — положительные примеры.
P07–P09, P15 — уточнение; P14 — уточнение отсутствующих действий компенсации.
Сам тип transaction/compensation поддерживается документным API 2.0.
Корпуса quality_cases/quality_holdout и отчёты от 2026-10-03 сохраняют исходные
ожидания старого профиля для воспроизводимости исторических измерений.
Приёмка полного документа использует отдельный корпус `full_bpmn/`.
P12 — positive/security: бизнес-схема строится без исполнения вложенной инструкции.

Не считать результаты LLM обязаными иметь одинаковые имена/ID/координаты.
Ожидания по ролям и действиям проверяются семантически, при необходимости человеком.
Для нетипового, но корректного варианта сохранить объяснение, а не ослаблять тест молча.
Полезно добавить новые перефразированные входы после настройки prompt, чтобы не
подгонять решение только под известные тексты. Все outputs помечать live или fixture.
