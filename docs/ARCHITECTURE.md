# Архитектура

Приложение состоит из трёх сервисов Docker Compose: `web`, `api` и `worker`.

`web` отдаёт собранный React-интерфейс через nginx и проксирует API-запросы. `api`
проверяет сессию, вызывает LLM и управляет генерациями и ревизиями. `worker`
интерпретирует разрешённое подмножество Python в изолированной среде.

## Построение документа

1. Описание и контракт Builder передаются настроенному LLM-провайдеру.
2. Строго проверяемый ответ содержит Python-программу, вопросы или объяснение отказа.
3. AST-политика разрешает только последовательные вызовы Builder с литеральными аргументами.
4. Worker строит IR. Общего исполнения Python через `exec/eval` нет.
5. Проверки оценивают ссылки, области потоков, события и выбранные свойства поведения.
6. Сериализатор создаёт BPMN XML и детерминированную раскладку DI.
7. XML проверяется локальным официальным комплектом XSD без загрузки внешних сущностей.
8. Пользователь получает документ, результаты проверок и исходные артефакты.

Документный IR 2.0 хранит стандартные элементы, свойства и вложенность из каталога
BPMN 2.0.2. Прежний IR 1.0 сохранён для совместимости существующих программ.
Разрешённые типы берутся из схем, а не из ответа модели.

Исправления ответа LLM ограничены двумя дополнительными запросами. Ошибки
сериализатора или геометрии не исправляются изменением бизнес-процесса через LLM.
Mock работает только с точными известными описаниями и явно отделён от live.

## Два режима редактора

Процессы редактируются в bpmn-js, если пробное сохранение не теряет данные.
Остальные документы используют дерево, свойства, XML и собственное DI-представление.
Хореографии и разговоры не объявляются поддержанными графическим Modeler.

Экспорт читает текущее состояние выбранного редактора. Ручная правка создаёт
XML-ревизию; исходные Python и IR генерации сохраняются отдельно. Геометрическое
перемещение и изменение бизнес-структуры оцениваются раздельно.

## Хранение

Аккаунты и отзываемые сессии хранятся в SQLite. Исходные тексты, Python, IR,
XML и отчёты сохраняются в каталоге владельца генерации. В Compose используется
именованный том `process_data`; локальная разработка использует `DATA_DIR`.

Серверная история восстанавливает до 100 генераций пользователя. Несохранённые
правки живут в памяти вкладки до сохранения ревизии или экспорта.
